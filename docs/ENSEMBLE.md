# Ensemble 协作行为标准

状态：生效。制定日期：2026-11-10。依据：用户明确提出的 coordinator 协作原则。
本标准适用于仓库内需要多人式协作的实质性任务；跨工具、聊天和额度恢复时同样适用。
仓库约束见 [AGENTS.md](../AGENTS.md)，当前移植检查点见 [恢复指南](migration/RESUME.md)。

## 1. 设计原则

Ensemble 是由一个主协调者负责整体、若干子体承担有界任务的工作方式。
拆分依据是业务职责、状态所有权和依赖关系，目标是让直接接手的人类也能理解设计、单独验证模块并完成集成。

**先有清楚的逻辑边界，再按边界委派；不要按可用子体数量切割代码。**
一个任务若必须让两个子体持续协商同一状态、反复修改同一接口才能完成，应先理清边界，或由主协调者本地完成。
文件不重叠是并发写入的必要条件，但不足以证明逻辑解耦。

衡量协作质量的是正确性、可读性、可维护性、证据完整性和接手成本，不是并发度或子体利用率。
不为委派新增框架、抽象层、重复状态或仅服务于协作工具的产品代码。

## 2. 职责与决策权

| 角色 | 负责 | 边界 |
|---|---|---|
| 主协调者 | 理解用户目标；架构与共享契约；拆分和依赖排序；分配写权限；解决冲突；审查 diff；集成、最终验证和交接 | 对整体结果负责，不能用子体的完成声明代替验收 |
| 实施子体 | 在指定边界内完成实现与相应测试；说明局部设计和风险 | 不擅自改变共享契约、产品范围、公共基础设施或其他 owner 的文件 |
| 调查/审查子体 | 在指定范围内提供可核对证据、结论和建议 | 默认只读；区分观察、推断与待验证项，不把建议当已获批决定 |

局部实现选择在任务约束内由子体自主决定，不必逐行审批。共享契约和架构变更由主协调者裁决。
超出用户授权的范围或需要用户作出的产品取舍，由主协调者带具体选项和影响说明向用户提出；正常集成不重复索要已获授权的许可。

## 3. 何时委派

适合委派的任务须有明确输入、独立产出和可观察的验收条件，例如：

- 只读调查某一模块的行为、兼容性证据或测试缺口。
- 依据已确定契约实现一个独立 adapter、纯算法或界面模块。
- 在不改共享实现的前提下，审查某项风险或准备一组独立行为测试。

简单修复、共享契约定义、紧耦合关键路径和集成冲突通常由主协调者本地完成。
独立调查可以与本地工作并行；实施任务只有在其所依赖的契约明确后才开始。
同一任务可以全程不启用子体；不要为了遵循本标准制造委派。

### 委派前的解耦检查

主协调者应能回答：

1. 这项任务承担什么业务责任，为什么能独立完成？
2. 它读取哪些输入，拥有哪份状态，输出什么，依赖哪些已确定的契约？
3. 成功、失败、取消、并发或过期结果各如何处理？只填写与任务有关的情况。
4. 哪些文件与运行资源归它写，哪些只能读？是否与正在进行的任务冲突？
5. 怎样独立证明结果正确，最终又怎样证明集成正确？

答不清时先补设计，不把不确定性分发给多个子体各自猜测。

## 4. 共享契约先于并行实施

共享契约至少说明相关的类型/接口、状态所有者、数据单位、生命周期和错误语义。
涉及持久化、异步或用户数据时，还应明确版本、保存/恢复、取消和身份/修订校验的责任。
已有契约直接引用，不另造一份容易漂移的说明。

主协调者先完成必要的最小契约修改及检查，再派发依赖它的实现。
子体发现契约不足时，报告具体调用场景、证据、建议修改及受影响任务；暂停依赖该决定的部分，可继续无关工作。
主协调者统一修改契约、通知所有消费者，再恢复执行。不得让多个子体各自添加不兼容的临时扩展。

## 5. 子任务单

每次委派必须传递下列信息。简单任务可以简写，但不能省略范围、写入边界、约束和验收条件。

```text
任务 ID / 名称：
目标：用户或系统最终可观察到什么结果。
基线：分支/提交、相关未提交改动、需要先读的说明。
逻辑边界：本任务的责任、输入/输出、状态所有者、明确不处理的内容。
依赖与契约：引用的接口/文档；哪些已确定，哪些必须等协调者完成。
允许修改：精确文件列表，或明确互斥的目录；新增文件范围。
只读 / 禁止修改：共享契约、其他 owner 文件、仓库配置等。
运行资源：独占输出目录、端口、缓存、进程；需要串行的检查。
约束：适用的仓库规则/技能；兼容、安全、离线、清理等要求。
验收：行为场景、预期结果、需要执行的检查及不能宣称的覆盖范围。
报告：改动文件、关键决定、测试命令/结果、未解决问题和交接状态。
```

读取必要上下文不受写入清单限制。超出允许修改范围时先报告原因，由协调者重新划分所有权，不能自行扩张。
每个活跃任务有可追踪的 ID 和 owner；有依赖的任务明确先后顺序，不以“同时开始”代替依赖管理。

## 6. 并发、文件与运行资源

- 同一时刻，一个文件或共享契约只有一个写入 owner。协调者也遵守此规则。
- 新增文件允许的目录互斥；测试、fixture、生成文件、lockfile、package scripts 和文档也属于写入范围。
- 两个任务即使改不同文件，若依赖同一未定语义，也应先定契约再并行。
- 变更所有权前，原 owner 先停止写入并交接落盘状态；新 owner 检查 diff 后接手。不能只靠发送通知假定对方已经停止。
- 共享工作树内 Git index 和 commit 默认由协调者管理；子体不执行 checkout/reset/stash、整树格式化或广泛 stage。需要独立提交时须先明确隔离方式和集成责任。
- 共享构建目录、测试用户数据、端口、缓存和进程树同样要避免冲突。影响相同输出的构建/测试串行运行，或使用已经设计好的隔离资源。
- 不回滚他人修改，不终止不属于本次任务的进程。清理遵循仓库移动至待删除目录的要求。

## 7. 子体交付报告

子体完成或被中断时，至少报告：

```text
状态：完成 / 部分完成 / 等待决定 / 基础设施阻塞。
改动文件：逐项列出，含新增文件；只读任务写“无”。
结果：具体实现或调查结论，附可定位证据。
关键决定：为什么这样做，是否影响既有契约；未确定内容单列。
验证：实际命令、结果、覆盖范围；失败和未运行的原因。
未解决问题：风险、缺口、需要协调者裁决的事项。
交接：是否已停止写入；仍运行的进程/资源、未提交变更和下一步。
```

“测试通过”必须对应实际执行的检查；缺失 fixture、未测平台和基础设施失败不能算通过。
子体完成只表示可交付审查，不表示整体任务完成。

## 8. 集成与最终验收

主协调者按依赖顺序集成，至少完成：

1. 核对报告与实际 diff，确认没有越界改动、重复实现或隐藏的共享状态。
2. 审查接口语义、错误/取消路径、生命周期、用户数据保护及代码可读性。
3. 检查多个任务连接处的行为；根据变更运行相关检查，不只收集各子体的局部通过结果。
4. 发现冲突时由明确的 owner 修复，不让多个子体同时修同一处。修复后重跑受影响的检查。
5. 验收通过后做小步本地 commit，更新实施状态和恢复记录；未验证事项保持显式未完成。

已通过的检查无需无理由反复运行；只有新修改、失败或未解决风险才扩大或重复验证。
整体完成声明必须基于集成后的代码与所需验证，不能以所有子任务标为完成作为充分条件。

## 9. 意外变化与失败升级

发现架构假设不成立、需要扩大共享契约或基础设施阻塞时，尽早报告，不靠连续重试隐藏问题。
报告包括失败操作、最小证据、已做诊断、影响范围和可行下一步。

对明确的瞬态故障，先检查是否已产生副作用，再进行有依据的有限重试；同一原因持续出现就交给协调者诊断或调整路线。
权限拒绝、构建环境缺失、工具不可用不能通过放宽产品安全约束、跳过断言或伪造通过来解决。
主协调者可处理授权范围内的技术调整；若必须改变用户目标/约束或需要外部操作，则向用户说明阻塞和所需决定。

## 10. 中断恢复与人类可接手性

任务较大或跨限额时，使用仓库实施文档保存任务状态；不要把唯一状态留在 agent 邮箱或聊天上下文中。
至少记录任务 ID、owner、输入/契约版本、允许修改文件、当前落盘状态、测试证据、未决问题和下一步。
主协调者结束前确认子体已停止或明确移交，不留下仍可能修改工作树的未知写入者。
恢复时先查 Git 和实际文件，再读记录；崩溃、额度耗尽或工具失败不代表之前没有写入。

最终设计应让一个没有参加过协作的人读出：

- 每个模块为什么存在、拥有何种状态、依赖谁。
- 一个用户操作如何经过输入适配、应用规则和领域逻辑到达结果。
- 失败、取消和恢复时由谁保持一致性。
- 哪些内容已实现并验证，哪些仍只是计划。

任务分工表帮助开发，不应渗入产品架构。移除所有子体名称后，模块边界、接口和测试仍应成立。

## 11. 当前移植的使用示例

恢复写可靠性 W1 的 pending/ACK、错误状态、恢复保护和 close/reset 生命周期互相耦合，先由主协调者确定模型并实施关键路径。
可以委派只读审查现有恢复测试或调查 host read/write 错误行为，报告缺口而不同时改 workspace 文件。
模型稳定后，若 host adapter 与 UI 提示能在互斥文件中依已定契约完成，再分别委派。
最终恢复流程、用户可见错误和并发保存行为仍由主协调者集成验证。

这个例子说明拆分方法，不改变 [移植实施计划](migration/IMPLEMENTATION.md) 的产品范围或下一步优先级。
